# 本轮 60 项的预期与计数

只有 RUN-001～RUN-060；SG 30 项，Role 30 项。每个 ID 对应一份独立 case YAML，
输入字段省略和显式配置分别保留；相同有效预算并不代表同一个输入场景。

## 每例共同预期

被更新范围的逻辑期望容量 D=3。SG 模式为三个组、每组一个 frontend Pod；
Role 模式为一个组、三个 frontend Role 实例，另有三个不变的 backend 实例。
本批 workerReplicas=0；Role 多worker完整性另有单元测试，不称为本批 Kind 覆盖。

1. 建立健康 A 的 UID 基线，开启四类资源的 List/Watch 后才提交 B。
2. 所有 B 必须保持 NotReady，直到 runner 按确切 Pod UID 放行。
3. 首停点允许启动 `min(U, 3-P)` 个旧实例，并持续观察10秒。
4. 每次只放行一个 B 逻辑单位；只有完整、非Terminating、实际Ready的 B 才提供容量信用。
5. 每条 Pod 事件都检查 `3 - 已启动旧实例数 + 当前Ready B数 >= 3-U`，
   同时检查实际Ready下限、活动数量≤3+S。旧Pod消失不释放信用。
6. 仍有符合条件的旧实例时，释放一个Ready信用后必须继续推进；不要求整批Ready。
7. 旧实例启动顺序固定为 P=0时2→1→0、P=1时2→1、P=3时不启动。
   partition保护的旧UID以及Role模式中backend UID全程不应改变。
8. 最终 A=P、B=3-P；全部剩余Pod健康。PG的所有者、关联、minMember/minResources，
   MS副本状态和revision引用必须收敛。P>0允许最终保留旧版本。

例如 U=0/S=1：旧实例不能先删；新surge先Ready才允许删除一个旧实例。
U=1/S=1时，新surgeReady后允许累计启动两个旧实例：这仍满足容量预算，
不能误报成“started累计数量超过1”。检查重点是未补回的容量缺口，而非累计替换次数。

PG提供SG更早的删除证据；跨资源流不存在本工具可以依赖的全序。
因此PG另有“U + 已显式放行单位数”的绝对上界，精确Ready预算在Pod流核算。
观察缺口不能判PASS；已锁存的任何过程违例不能被健康终态覆盖。
