## 命名与同步 / Naming and synchronization

- 正文采用 `<topic>.<language>.md`，topic 使用小写 kebab-case；language 为 `en` 或 `zh-CN`。README.md 是双语入口，SOURCES.json 是机器可读来源清单。
- 版本写在正文和 SOURCES.json，不放入文件名；目录只保留每个语言的最终版本，旧内容从 Git 和原始来源追溯。
- 两种语言共享 API 节号、SG 设计 ID、数值表和语义范围。修订必须同时维护两份；叙述可以适应语言，不能产生不同的默认值、约束或例外。
- 语义修订按 workspace 审批流程，记录批准原文、前后规则、受影响用例和验证；不得从实现或失败结果自动改写规范。更新正文后同步 SHA256/字节数，保留原始导入来源。

Use `<topic>.<language>.md`, with lower-case kebab-case topics and `en` / `zh-CN` locales. Keep versions inside documents and SOURCES.json, preserving stable links. Maintain both editions in the same change, with matching clause numbers, scenario IDs, numeric tables and semantics. Record explicit semantic approval and provenance; never regenerate expectations from observed implementation. Earlier editions remain recoverable from Git or the recorded original sources.

**2.13（2026-11-23）**：用户明确口径：“controller不在时丢了pod，这个有一个非赦免场景，即controller升级场景，赦免的是完全故障或者删除后的修改，升级过程、主备切换、多副本删除主（节点故障）等过程，这些都算在正常运行的容灾范围内”，并说明完全故障也恢复可行、第一次升级缺口接受、grace计时可以赦免。原规则不分controller为何不在，无标记离线缺失一律只补缺。现规则：升级、主备切换、多副本时主实例被删除或其所在节点故障的空窗内丢失的无标记Pod，继任实例接管后视同连续运行时的真实Pod删除，按recoveryPolicy范围恢复；完全故障期间和controller被删除之后的丢失允许只补缺，也允许按范围恢复；均不超出策略范围；首次升级到实现本条的版本时允许只补缺。新进程grace重新起算、deletion-scope续删与RC-01～04、Terminating、预算、历史模板和None只补缺不变；SG A.5与API §6.2关于成员表和创建事实的限制本版未改，继任者据何得知Pod曾经存在待单独决定。同版本重启、单副本实例被删除或其所在节点故障、副本数调为0后恢复、升级未能完成且其后长时间没有任何实例能够工作的归类待定，归类之前只补缺或按范围恢复均符合；条文中属于现有条文延伸的写法（见009 proposal第9节）待用户确认。本次仅更新契约：据代码静态阅读（未执行），现有上游与在网实现在不赦免的空窗内只补缺，尚未符合；runner尚无对应可执行用例，既有结果不构成本版通过或失败证据。批准原文、2.12快照、前后规则、受影响用例及验证归属见 [009 proposal](../../../issues/features/009-runner-contract-offline-loss-scope-IP/PROPOSAL_COMMIT.md)。取代2.6“健康幸存实例保留”、2.9“允许重启期间删除事件丢失并按当前事实补缺”与2.11“无标记的离线缺失仍补缺”中不区分原因的部分。

**2.13 (2026-11-23):** The user clarified which Pod losses during controller absence are exempt. An upgrade, a leader switch, and deletion or node failure of the leader among multiple replicas fall within the fault tolerance expected of normal operation and are not exempt; a complete controller failure and changes after the controller was deleted are exempt. Recovering at the policy scope after a complete failure is also acceptable, the first-upgrade gap is accepted, and grace timing stays exempt. Previously every unmarked offline loss was refilled regardless of cause. Now the successor handles an unmarked Pod lost during a non-exempt gap as an actual Pod deletion seen in continuous operation and recovers at the recoveryPolicy scope. Exempt losses may be refilled or recovered at that scope; recovery never goes beyond it; the single upgrade to the first implementing version may refill only. New-process grace, marked deletion continuation and RC-01–04, Terminating occupancy, budgets, historical templates and refill-only None are unchanged. The SG A.5 and API 6.2 limits on member tables and creation facts are not modified; how a successor learns that a Pod existed awaits a separate decision. The classification of a same-version restart, deletion or node failure of a single-replica instance, scaling the controller to zero and back, and an upgrade that does not complete and then leaves no instance able to work for an extended period is pending, and until then refilling and recovery at the scope both conform; wording that extends existing clauses (listed in section 9 of the 009 proposal) awaits user confirmation. This is a contract-only update: by static code reading (not executed), current upstream and deployed implementations only refill in non-exempt gaps and do not yet conform; no executable runner case covers them, and existing results are neither passes nor failures for this version. See the [009 proposal](../../../issues/features/009-runner-contract-offline-loss-scope-IP/PROPOSAL_COMMIT.md) for the verbatim approval, version 2.12 snapshots, old/new rules, affected cases and verification ownership. This supersedes the cause-independent parts of 2.6 “healthy survivors remain”, 2.9 “may refill after missed offline deletion events” and 2.11 “unmarked offline losses still refill”.
